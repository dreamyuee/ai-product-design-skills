# 产品流程完整性检查

在产品方案、PRD、交互设计或流程评审中，逐步骤执行以下七项检查。与其他产品 skill 配合使用；不要只检查主路径或只列通用清单。已有规则以用户确认和当前证据为准，把未知规则标记为“待确认”，把建议明确标记为“建议”。不要把建议写成已实现行为。能访问代码或产品时，先只读核对当前行为，减少不必要的“待确认”。

## 执行流程

1. 明确用户目标，列出流程步骤、分支与终点。针对用户提供的局部流程完成检查，不为检查而扩大范围。
2. 区分页面展示、用户动作、服务端持久状态、异步任务状态。点击按钮、看到成功动画、请求发出，都不能单独作为业务提交成功的依据。
3. 对每一步填写七项检查；不适用时写明原因，不留空。
4. 对跨步骤规则检查一致性，优先解决丢进度、误跳步、重复扣费/发奖、重复创建任务、失败后无路可走的问题。
5. 输出可交付给设计和开发的规则、验收场景和待确认事项。用业务语言解释技术概念，必要时给字段示例，不声称它们是现有架构。

## 每一步固定检查

| 检查项 | 必须回答 |
| --- | --- |
| 进入条件 | 谁能进入？前置步骤和权限是什么？直接链接、返回、刷新、登录失效后如何处理？不满足条件去哪里？ |
| 提交成功条件 | 哪个业务事实或服务端确认才算成功？校验与保存发生在何时？等待期间显示什么？何时允许进入下一步？请求超时但结果未知时如何查证？ |
| 跳过 | 是否允许？跳过后去哪里？是否可补填、从哪里补填？是否影响后续功能或奖励？如何区分未开始与主动跳过？ |
| 退出恢复 | 关闭、刷新、返回、重新登录后恢复到哪里？未提交输入是否保留？已提交答案与进行中任务如何恢复？保存范围、期限和跨设备规则是什么？ |
| 失败重试 | 校验失败、网络错误、超时、服务端失败分别如何提示？保留什么？重试哪个动作？是否产生额外费用？不可重试时如何退出或求助？ |
| 重复操作 | 连点、返回重提、刷新、多标签页、多设备、重复回调会怎样？如何避免重复任务、扣费、奖励或记录？按钮禁用只是前端反馈，涉及业务副作用时还需服务端去重。 |
| 后台记录 | 为恢复和业务正确性必须保存哪些状态、答案、标识、时间与结果？在哪个事件保存？谁是权威来源？分析埋点另记哪些事件？不要用埋点代替业务状态。 |

## 相关时补充检查

- **A/B 分组**：刷新、换设备、重新登录后是否留在同一组，曝光何时记录。
- **流程改版**：进行到一半的老用户继续旧流程、迁移到新流程，还是重新开始。
- **离开后的结果**：异步任务完成或失败时，用户不在页面上如何得知，从哪里回到结果。

## 状态和恢复规则

- 按业务需要选择状态，例如 `not_started / in_progress / submitted / skipped / failed`；不要强行使用所有状态。对异步任务单独区分已受理、执行中、成功、失败。
- 优先根据服务端确认的步骤状态推导下一步；如保存当前位置，同时明确它与步骤状态冲突时的处理规则。
- 明确输入草稿与已提交结果的边界。允许编辑时说明编辑是否影响后续步骤、奖励与已有任务。
- 对提交后响应丢失的情况，先查询已有结果或用同一请求标识安全重试，避免直接创建第二次业务动作。
- 对跨标签页或跨设备冲突，明确采用最新已确认状态、版本校验或冲突提示中的哪一种；只在相关场景需要时展开。

## 后台记录输出

按需要给出字段级建议，使用“字段—作用—写入时机—恢复时用途”的形式。最少覆盖：

- 用户/流程实例/步骤标识与流程版本（如存在版本变化）。
- 步骤状态、已提交答案、必要的草稿与更新时间。
- 提交结果或任务标识、失败原因、请求去重标识（涉及副作用时）。
- 奖励或扣费流水、对应业务事件与发放/扣费结果（涉及 credits 时）。余额展示与到账成功分开定义，不因刷新重复发奖。

单列分析事件，如进入、提交尝试、提交成功、跳过、恢复、失败、重试。明确成功事件应以业务成功为依据，避免一次点击被计成完成。只记录必要数据，不建议在埋点中写入完整敏感输入。

## 默认交付格式

先用简短文字指出影响最大的流程缺口，再按步骤输出七项短列表，因为八列表格放进 PRD 后很难阅读。只有内容很短的简单流程才用表格。随后补充：

1. 跨步骤规则与必要的后台字段建议。
2. 可验证的验收场景：给定状态 → 用户动作/异常 → 页面结果 → 后台结果。
3. 仅列影响决策的待确认问题；为不阻塞的未知项给出明确标注的默认建议。

局部文案或单个按钮修改时，在相关步骤内简要检查七项，只展开受影响项；不要输出无关的长篇技术清单。

## 校准示例：两题 onboarding

检查以下情况，不能只写“记录当前步骤”：

- 第一题未提交就关闭：依据草稿规则恢复第一题，不能记为主动跳过。
- 第一题提交且服务端确认成功后关闭：恢复第二题，保留第一题答案。
- 第一题跳过并保存成功后关闭：恢复第二题，将第一题记为 skipped；补填入口与资格需明确。
- 第一题已保存但客户端未收到响应：再次进入时查询状态，不能要求重复完成或重复发奖。
- 连点提交或多标签页重复提交：业务结果只执行一次，重复请求返回已有结果。

以上为建议规则示例，遇到已有产品决策时按其调整；不自动把“跳过后可补填”等未确认能力写成事实。
