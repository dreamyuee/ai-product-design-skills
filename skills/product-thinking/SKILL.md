# 产品思考

从具体用户、场景与行为出发，解释设计为何成立、适用于谁、代价是什么、如何实现和验证。产品思考独立于当前项目，不默认关联任何特定产品。

## 先选模式

需求常以方案的形式出现。问题没确认前写满页面和字段，会让团队在错误方向上讨论细节，所以先判断处于哪个阶段：

- **问题诊断（默认）**：用户问要不要做、为什么流失，或贴来反馈和观察。输出问题在哪、证据、假设和下一步验证，不展开页面和字段。
- **方案比较**：问题已确认，需要选方向。比较 2–3 个方案，包含最低改动版本，给出推荐。
- **完整交付**：用户明确要 PRD、完整方案，或方向已选定。交付下文八项。

用户没有说明时从问题诊断开始，并在结尾说明进入下一模式还缺什么。

## 观察与证据

保留用户原始观察，另列可确认事实、助手推导、待验证问题与可迁移启发。区分截图可见、实际操作验证、官方声称和设计建议。不把竞品意图、功能猜测或客户评价写成已证实结论。

使用竞品时先说明样本范围：看了哪些、哪些实际走过、哪些只看官网。尽量覆盖已有的全部相关样本，并纳入不支持当前结论的反例，因为只挑典型几家很容易得出过于绝对的结论。

截图不可读时说明分析仅基于描述。用户要求完整阅读文章或字幕时，取得全文后再分析；无法取得则说明阅读范围。

如果用户指定了产品笔记（如 Notion、飞书或本地文档），具体案例与后续证据记录在那里：写入前读取当前结构并避免重复。此 skill 保留方法，笔记保留案例、来源和假设；只有用户要求记录时才写入，单纯分析不写入。笔记不可用时告知用户，不影响分析。

## 用户、场景与价值

明确谁被什么事件触发、想完成什么、目前如何完成、受到什么约束、得到结果后还要做什么。按会改变流程、信息、规则、风险、成本或商业价值的差异分群，避免无意义 Persona。

用一句话描述用户为什么再次使用产品，拆成 2–3 个对应具体动作或场景的关键词，为每个词配真实指标。不使用“提供价值”“提升效率”等空话。不预设必须每天打开产品；后台与周期任务关注按期完成、结果采用和持续授权。

用户不创建、不连接或不复用时，分别诊断动机、触发与行动成本：任务是否真实且值得做；此刻是否意识到能力适用；识别场景、输入、授权、试运行、修正及维护是否过重。不凭低点击率直接判定没有需求。详细观察方法见 [产品体验观察](references/product-experience.md)。

## Agent 产品：从 Task 向下分析

先从“用户要完成什么 Task”开始，再依次问：需要什么 Input → 什么 Tool → 是否需要 Connector → 默认 Agent 能否完成 → 哪些必须 deterministic（确定性执行）→ 哪些值得交给模型判断。此顺序用于发现依赖，后续发现能力缺口时回到前面修正；不要先建 Agent 再寻找用途。

1. **Task**：明确目标、交付结果、成功标准、一次性或周期执行，以及任务边界。
2. **Input**：列出必需输入、已有上下文、预填来源、缺失补问、格式校验和数据时效；只收集推进任务必需的信息。
3. **Tool**：明确每一步需要的检索、计算、读取或写入能力，实际支持的参数、返回值、失败和调用成本；无可用工具时标记能力缺口，不靠模型臆造结果。
4. **Connector**：判断工具是否依赖外部账号或私人数据。Tool 是执行能力，Connector 是接入与授权机制，两者不必一一对应。公开数据任务可能无需用户连接；依赖授权时按需申请并提供恢复路径。
5. **默认 Agent**：先验证现有 Agent 加任务模板、参数和工具配置是否足够。新输入、新对象、新频率通常是新 Task；固定补问、步骤和格式可做任务模板。只有长期职责、规则、权限/数据隔离、状态或独立评测维护确有需求时再考虑新 Agent。核实当前产品对这些对象的实际定义，不把概念划分当作代码事实。
6. **确定性执行**：权限与租户隔离、额度/预算、扣费、参数校验、调度、状态迁移、幂等、重试上限及外部动作执行由明确规则和程序约束；精确计算交给确定性工具。不能仅靠 Prompt 保障这些边界。
7. **模型判断**：仅在语义理解、意图提取、非结构化信息归纳、内容生成、匹配或不确定路径规划有收益时使用。定义输入、输出约束、质量评价与失败回退；歧义影响权限、费用或不可逆动作时让用户澄清或确认。模型提出工具调用，系统仍校验权限、参数和预算后执行。

需要落地时输出“Task/成功标准 → Input → Tool → Connector/权限 → 默认 Agent 复用或新增依据 → 确定性规则 → 模型判断 → 失败恢复/成本”的对应表。按步骤拆分责任：同一任务通常同时包含确定性部分和模型部分，不将整个任务笼统归为其中一类。

## 产品决策评估：六个必查维度

1. **用户价值**：解决什么真实问题，哪类用户在什么场景获得什么具体结果，相比替代做法改善什么。
2. **商业价值**：影响激活、留存、付费的哪个指标，是否符合目标 ICP，用户结果如何产生复用和付费理由。
3. **成本与收益**：开发、维护、模型 Token、API、工具调用、Credits 与规模化成本；区分一次性与持续投入，评估单位成功用户成本和长期收益，计入失败、重试及未转化用户消耗。
4. **技术可行性**：现有能力是否支持，前后端、数据与第三方服务需改什么，哪些可复用，如何低成本验证。
5. **风险与边界**：隐私、权限、滥用、成本失控、错误结果、失败及恢复如何控制。
6. **验证方式**：区分事实、推断与假设，说明数据、成功标准、统计口径和观察周期。数据不足标记「待验证」，不编造金额、能力或因果关系。

涉及 AI Agent、Credits、API、Connector 时，必须评估执行成本、累计调用、额度、并发、频控、授权撤销、循环与重试、重复扣费及免费额度套利。区分 Credits 与实际货币成本。

涉及 Connector 或外部动作时，按 Just-in-time permission（按需授权）评估申请时机：任务真正依赖某项数据或动作时，再请求所需权限。区分连接推荐、权限授予和具体动作批准；已有有效授权范围内不重复弹窗。读取 [按需授权规则](references/product-experience.md#按需授权just-in-time-permission)，补全拒绝、失效和恢复路径。

## 产品方案必须完整到可落地

完整交付模式下同步交付以下八项，不省略影响落地的关键决策。问题诊断和方案比较模式只取其中相关项。

### 1. 完整方案

给出页面结构、完整问题与选项、表单字段、默认值、必要文案、交互状态和用户流程。多任务方案给完整任务清单和各任务补问表格，不用少量示例代替。

每个字段说明名称、用途、必填性、输入形式或选项、默认值、校验、预填来源及缺失时如何继续。说明点击后去哪里、是否自动发送或执行、结果如何承接。

### 2. 业务逻辑

讲清楚用户每次选择后，系统如何响应：推荐哪些任务、继续问什么、使用什么执行能力、什么时候需要连接账号，以及最终交付什么。说明推荐不合适、用户改选或跳过时怎么办。涉及 Agent 和 Connector 时，再补充具体选择规则。

需要时用表格把用户/场景、任务、补问字段、执行能力、Connector 与结果逐项对应。解释哪些由产品预设、哪些由系统判断、哪些让用户决定；不使用抽象术语代替具体规则。

### 3. 技术实现

分清可复用能力、仅需改配置/Prompt/模板的部分、必须新增的前端/后端/数据/集成和待确认依赖。

任务数量不等于 Agent 数量。优先复用执行能力、任务模板、参数和工具配置；只有能力、权限、状态或质量要求存在明确差异时拆分独立 Agent。给出推荐架构及拆分依据，不把建议写成现有能力。

### 4. 成本评估

评估开发维护、Token/API/工具、Credits 及规模成本；说明成功、失败、重试消耗、使用量假设、预算控制和单位激活成本。缺少数据时给计算口径与缺失参数，标「待验证」。

### 5. 异常与边界

覆盖跳过、返回改选、失败、重试、中断恢复、重复提交、权限不足、授权失效和额度不足。逐项说明用户看到什么、能做什么、保存哪些数据、是否重新执行或扣费及恢复路径。

涉及流程设计时配合已有 check-product-flow（产品流程完整性检查），检查进入条件、提交确认、跳过、退出恢复、失败重试、重复动作和后台记录。该 skill 不可用时，至少覆盖上一段列出的情况，并告知用户未做逐步检查。保持两个 skill 的分工，不重复创建同功能 skill。

### 6. 方案取舍

比较可行替代方向，必要时包括维持现状与最低改动方案。每个方案至少给一个主要收益、一个潜在代价和一个验证指标。说明开发依赖、适用条件、推荐理由、当前做什么和延后什么及其后果。

### 7. 验证指标

定义成功率、转化率、留存和单位激活成本的适用口径；说明成功事件、分母、周期与数据来源。激活对应真实用户结果，不能只用页面完成或点击替代。单位激活成本计入观察期内未激活用户的相关消耗，并明确成本范围。同时设置成本、失败率、质量和打扰程度护栏。

### 8. 主动发现矛盾与隐藏成本

首次提出方案时主动检查并调整推荐，不等用户或其他 PM 指出后补充：

- 用户目标与业务目标是否冲突；任务清单是否超出现有能力。
- 承诺是否依赖尚未取得的数据或权限。
- 前端减步骤是否增加后台复杂度、默认执行或误操作。
- 免费体验是否不可持续；个性化是否导致模板、Agent 和维护膨胀。
- 转化增长是否损害质量、信任和长期留存。
- 不同入口、页面、配置与规则是否矛盾。

说明影响、解决办法与剩余不确定性，不能仅列风险而不改变方案。

**Onboarding 交付基准**（仅完整交付模式）：同步给全部页面问题和选项、推荐任务页的完整任务清单及推荐/排序/兜底规则、各任务补问表格、执行能力与 Connector 对应、Agent 复用架构（避免为 30 个任务分别开发 30 个独立 Agent）、最低开发成本版本、Credits/运行成本、异常恢复及指标。未知项明确标记，不用方向性建议代替交付。

## 指标与证据判断

区分访问/点击/创建、执行量、任务成功、结果采用、回复、预约、销售机会、成交和持续付费；不同阶段不能互相替代。比较数据需检查对象、时间、分母、基线与来源。入口用户使用量更高不能单独证明入口造成增长，客户案例不能证明普遍因果。

写出分子和分母，并判断样本是否足以得出结论。低流量或低频事件（如付费）很难用 A/B 在短期内看出差异，此时改用前置指标、前后对比或定性验证，并说明结论强度。

## 输出顺序

- 问题诊断：结论 → 问题 → 证据（事实与推断分开）→ 假设 → 下一步验证 → 还不确定的。
- 方案比较：结论 → 用户价值 → 商业价值 → 成本与风险 → 方案取舍 → 验证指标。
- 完整交付：在方案比较的顺序上，把八项放进相应部分或附表。

保留清晰判断，不机械输出全量清单。
